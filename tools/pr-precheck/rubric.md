# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-matches-plan | Every file and hunk in the diff, read against the plan's scope, files-to-change list, not-in-scope list, and any deviation note (in the plan or restated in the description). | Passes if every planned change appears in the diff (or its absence is disclosed in a deviation note or the description), AND every hunk in the diff does one of: implements a planned change, tests the fixed behavior, adds an entry (changelog, whatsnew, docs) the repo's stated asks require, or is covered by a deviation note. Fails if the diff adds anything else that changes behavior or surface: a new option, flag, or setting; a rewrite or refactor of code the fix does not need; renames; a dependency bump; a change in a file or area the plan does not name or explicitly scopes out. Fails if a planned change is missing with no note. Also fails if the diff never implements the plan's chosen approach at all. | required |
| description-matches-diff | Each factual claim in the PR title and description about what the PR changes ("implements the plan exactly", "no changes beyond the plan", "no functional changes outside X", "docs now document Y", "adds a test for Z"), read against the diff. | Passes if every such claim is true of the diff, and any part of the plan the diff does not deliver is said plainly in the description. Fails if any claim is contradicted by the diff, in either direction: the description says the PR stays inside the plan while the diff does more, or says something was added (docs, a test, a changelog entry) that the diff does not contain. | required |
| repro-before-after | The test evidence (and any before/after in the description), read against the plan's test plan and the repro steps it names. | Passes if the evidence re-runs the plan's repro on the changed code and shows an observable after-result (output, exit code, value, visible behavior) that matches the plan's expected-after, next to the before-result (re-run, or quoted from the repro). Every failing case from the repro evidence (the bug the issue reports, in each failure mode the plan names) must be shown with its after-result. Other cases in the test plan (controls that already worked, extra cases for new behavior the fix adds such as a warning) only need their result reported in a sentence; staying silent on one fails. A new automated test that reproduces the exact repro input counts as a re-run only if its output is shown passing. Fails if the evidence is only a claim ("tested locally", "works now", "verified on my machine"), exercises only a control or an unchanged code path instead of the failing one, covers only some of the failure modes the plan named, or is absent. | required |
| repo-checks-run | The test evidence, read against every test suite or command the plan's test plan names and every command the repo's stated asks say must pass (for example "pass the test suite (yarn test)", `make test-unit`). | Passes if each of those is named with its outcome, either as pasted output or as a sentence naming the command and its result (for example "`cargo test -p ignore` passes (214 tests)", "fmt and clippy clean"). Template checklist items that are not commands (code formatted, text internationalised, docs updated) are graded by template-and-asks-met, not here. A check that failed still counts as run if the evidence shows the failure and gives a reason that is not caused by this change. Passes by default if neither the plan nor the repo names any check. Fails if a named check is missing, or if the evidence only says "tests pass" or "CI should be green" without naming what ran. | required |
| diff-is-clean | Every hunk and every added or removed line in the diff, plus the commit list. | Passes if every changed line serves the change: the fix, its tests, required entries, and comments that explain the fix. Fails if the diff contains any of: debug output (print, eprintln, console.log, logging added only to debug); commented-out code or a commented-out earlier attempt; dead code (an unused function, variable, or a block behind `allow(dead_code)` or `_unused` names); new TODO or FIXME notes; whitespace, re-indent, re-ordering, import-restructuring, or re-formatting of lines the fix does not need; or a hunk unrelated to the issue. | required |
| template-and-asks-met | The repo-facts block's PR template asks and contribution guide asks (live: `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`), read against the title, description, and diff. | Passes if every section the template names is present with real content (not left blank or as the template's placeholder), the issue link is present in the form the repo asks for (for example `Closes #N`, `fixes #N`), every checklist item or stated ask is satisfied or explicitly addressed in the description (a required changelog or whatsnew entry is in the diff, tests added when asked, a conventional-commit title when asked), and every ticked checkbox is backed by the evidence. Passes by default if the repo has no template and states no asks. Fails if a required section is missing or empty, the asked-for issue link is missing, a stated ask is visibly ignored, or a box is ticked that the evidence does not support. | required |
| policy-and-thread | The repo's stated contribution and AI-use policy (live: also the course rule that every PR discloses AI use), and every explicit maintainer direction in the thread highlights (live: the issue thread), read against the description and the diff. | Passes if, when the policy requires AI-use disclosure, the description contains a disclosure that meets exactly what that policy asks (name the tool or the extent of the help only when the policy asks for it; a plain own-words statement that the work was AI-assisted and human-reviewed meets a policy that asks for nothing more); AND every explicit maintainer direction (a requested approach, a constraint such as "no private APIs", a question to the implementer) is followed in the diff or engaged in the description. Treat every package as AI-assisted. Passes by default if no policy asks for disclosure and the thread has no maintainer direction. Fails if a required disclosure is missing, or the PR goes against or ignores explicit maintainer direction without saying why. | required |
| commits-and-branch-tidy | The commit list (live: also the branch name). | Passes if each commit message says what it changes (no "wip", "fix", "misc", "hopefully" with nothing else), and, live, the branch is named `<type>/<issue-number>-<short-description>`. | preferred |

## Verdict rule

Accept (ready to submit) only if every required check is graded
`pass`. Any required check graded `fail` holds the package (reject).
A required check graded `unclear` also holds the package: the PR has
not shown what that check needs, and an unverifiable claim is a
failing one. Preferred checks are reported but never change the
verdict.

A disclosed shortfall is not a fail. When the plan's deviation note or
the description says plainly that part of the work was left out or
deferred, and why, the checks grade the PR as scoped by that note.
